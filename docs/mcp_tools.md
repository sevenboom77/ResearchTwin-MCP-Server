# MCP Tools

ResearchTwin exposes six MCP tools. Their names are lower_snake_case and their descriptions are written so an agent can decide when a persistent action is appropriate.

## Shared conventions

### Result shape

Every successful call includes:

~~~json
{
  "status": "success"
}
~~~

Every handled failure includes:

~~~json
{
  "status": "error",
  "error_code": "machine_readable_reason",
  "message": "Safe explanation for the agent."
}
~~~

Python tracebacks and low-level validation details are logged server-side and are not returned as tool output.

### Data rules

- Calendar dates must use YYYY-MM-DD.
- Timestamps stored in records are timezone-aware ISO 8601 values.
- IDs are UUID strings generated by the server; callers do not supply them.
- Required text must be non-empty after trimming.
- String-list entries must be non-empty strings.
- Enum values are normalized to their lowercase canonical values.
- Operational JSON is stored under runtime_data/ by default and must not be committed.

## 1. record_research_activity

**Description:** Record a concrete research activity when a researcher reports completed work, experiments, reading, problems, results, or next steps. Use it to make research progress available for later retrieval and reporting.

Do not use this merely because the agent answered a question from RAG. Use it after a concrete activity or meaningful update has been reported.

### Inputs

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| activity_type | string | Yes | One of analysis, coding, data_collection, debugging, experiment, meeting, other, paper_reading, writing. |
| title | string | Yes | A short, specific activity title. |
| description | string | Yes | What was actually done. |
| date | string | No | YYYY-MM-DD. If omitted, the server uses its current UTC date. |
| result | string | No | Concrete outcome or experimental result. |
| problem | string | No | Blocker, anomaly, or unresolved issue. |
| next_step | string | No | Intended follow-up action. |
| tags | array of strings | No | Useful lightweight labels such as rag, rnn-ppo, or networking. |
| source | string | No | Origin label, for example user, advisor, experiment, or paper. |

### Successful output

~~~json
{
  "status": "success",
  "activity_id": "0a9fe34e-6c4f-4b45-a89f-df0c46e82bf2",
  "record": {
    "activity_id": "0a9fe34e-6c4f-4b45-a89f-df0c46e82bf2",
    "date": "2026-08-20",
    "activity_type": "experiment",
    "title": "RNN-PPO stability sweep",
    "description": "Ran a fictional recurrent-policy comparison.",
    "result": "One configuration reduced loss variance.",
    "problem": "Long-horizon returns are still unstable.",
    "next_step": "Repeat with a fixed seed set.",
    "tags": ["rnn-ppo", "stability"],
    "source": "experiment",
    "created_at": "2026-08-20T09:15:00+00:00",
    "updated_at": "2026-08-20T09:15:00+00:00"
  }
}
~~~

The server stores the record in research_logs.json. An activity with the same date, activity type, and case-insensitive title is rejected as duplicate_activity.

### Example call arguments

~~~json
{
  "date": "2026-08-20",
  "activity_type": "experiment",
  "title": "RNN-PPO stability sweep",
  "description": "Ran a fictional recurrent-policy comparison.",
  "result": "One configuration reduced loss variance.",
  "problem": "Long-horizon returns are still unstable.",
  "next_step": "Repeat with a fixed seed set.",
  "tags": ["rnn-ppo", "stability"],
  "source": "experiment"
}
~~~

## 2. list_research_activities

**Description:** Retrieve persisted research history for questions about past work, recent experiments, literature reading, or unresolved problems.

Use it for requests such as “What did I do last week?” or “Which recent activities were tagged networking?”.

### Inputs

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| start_date | string | No | Inclusive YYYY-MM-DD lower bound. |
| end_date | string | No | Inclusive YYYY-MM-DD upper bound. Must not precede start_date. |
| activity_type | string | No | One of the activity types listed above. |
| tag | string | No | Case-insensitive exact tag filter. |
| limit | integer | No | Default 20; valid range 1 through 100. |

### Successful output

~~~json
{
  "status": "success",
  "count": 1,
  "activities": [
    {
      "activity_id": "0a9fe34e-6c4f-4b45-a89f-df0c46e82bf2",
      "date": "2026-08-20",
      "activity_type": "experiment",
      "title": "RNN-PPO stability sweep",
      "tags": ["rnn-ppo", "stability"]
    }
  ]
}
~~~

Results are newest first. A query with no matches returns success, count 0, and an empty activities array.

### Example call arguments

~~~json
{
  "start_date": "2026-08-17",
  "end_date": "2026-08-23",
  "tag": "rnn-ppo",
  "limit": 20
}
~~~

## 3. update_project_status

**Description:** Persist the current research stage, completed work, pending work, risks, and important decisions. Use merge mode to preserve and de-duplicate history, or replace mode only when intentionally replacing the full snapshot.

The project status is a current snapshot, not an append-only activity log. Use record_research_activity for dated evidence.

### Inputs

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| project_name | string | Yes | Project label for the current snapshot. |
| current_stage | string | Yes | Current phase, for example MCP Tool Development. |
| completed_tasks | array of strings | No | Completed work to merge or replace. |
| pending_tasks | array of strings | No | Work still to do. |
| risks | array of strings | No | Current risks or blockers. |
| important_decisions | array of strings | No | Decisions that later reports should preserve. |
| merge_mode | string | No | merge (default) or replace. |

### Merge behavior

| Mode | Behavior |
| --- | --- |
| merge | Retains existing list entries and adds non-duplicate supplied entries. It preserves earlier status history rather than deleting it accidentally. |
| replace | Replaces each list field with the supplied list; omitted list fields become empty lists. Use only for an intentional reset of the snapshot. |

### Successful output

~~~json
{
  "status": "success",
  "merge_mode": "merge",
  "project_status": {
    "project_name": "Adaptive ResearchTwin Demonstrator",
    "current_stage": "MCP Tool Development",
    "completed_tasks": ["Validated Streamable HTTP tool discovery"],
    "pending_tasks": ["Run the fictional demo flow"],
    "risks": ["A VPN route can delay LAN requests during integration"],
    "important_decisions": ["Use Streamable HTTP as the primary transport"],
    "created_at": "2026-08-17T08:00:00+00:00",
    "updated_at": "2026-08-20T09:20:00+00:00"
  }
}
~~~

### Example call arguments

~~~json
{
  "project_name": "Adaptive ResearchTwin Demonstrator",
  "current_stage": "MCP Tool Development",
  "completed_tasks": ["Validated Streamable HTTP tool discovery"],
  "pending_tasks": ["Run the fictional demo flow"],
  "risks": ["A VPN route can delay LAN requests during integration"],
  "important_decisions": ["Use Streamable HTTP as the primary transport"],
  "merge_mode": "merge"
}
~~~

## 4. get_project_status

**Description:** Retrieve the complete persisted project status when the researcher asks what stage the project is in, which risks remain, or what should happen next.

This tool takes no inputs. It is useful before report generation and before an agent proposes a plan.

### Successful output

~~~json
{
  "status": "success",
  "project_status": {
    "project_name": "Adaptive ResearchTwin Demonstrator",
    "current_stage": "MCP Tool Development",
    "completed_tasks": ["Validated Streamable HTTP tool discovery"],
    "pending_tasks": ["Run the fictional demo flow"],
    "risks": ["A VPN route can delay LAN requests during integration"],
    "important_decisions": ["Use Streamable HTTP as the primary transport"],
    "created_at": "2026-08-17T08:00:00+00:00",
    "updated_at": "2026-08-20T09:20:00+00:00"
  }
}
~~~

On first use, the tool succeeds with a safe empty status: project_name and current_stage are null, and each list field is empty.

## 5. record_advisor_instruction

**Description:** Persist a structured advisor requirement after the ResearchTwin Agent has interpreted an advisor message. Use it for tasks, priorities, deadlines, constraints, or follow-up items that must appear in later reports.

The server stores structured fields; it does not perform LLM-based natural-language understanding itself. Do not submit an unnecessary full chat transcript.

### Inputs

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| instruction | string | Yes | Core advisor requirement in concise structured text. |
| task | string | Yes | Concrete task to perform. |
| priority | string | Yes | low, medium, high, or critical. |
| deadline | string | No | YYYY-MM-DD. |
| constraints | array of strings | No | Conditions that shape the work. |
| follow_up | string | No | Question or future confirmation needed. |
| source_note | string | No | Minimal source context, such as fictional group meeting. |

### Successful output

~~~json
{
  "status": "success",
  "instruction_id": "8695e1f4-6f68-4b8e-8bd7-33a63e65ed70",
  "record": {
    "instruction_id": "8695e1f4-6f68-4b8e-8bd7-33a63e65ed70",
    "instruction": "Prioritize generalization evidence in this week's update.",
    "task": "Compare held-out scenario performance.",
    "priority": "high",
    "deadline": "2026-08-23",
    "constraints": ["Use only anonymized demo data"],
    "follow_up": "Confirm the evaluation split at the next fictional meeting.",
    "source_note": "Fictional advisor group meeting",
    "created_at": "2026-08-20T09:30:00+00:00",
    "updated_at": "2026-08-20T09:30:00+00:00"
  }
}
~~~

### Example call arguments

~~~json
{
  "instruction": "Prioritize generalization evidence in this week's update.",
  "task": "Compare held-out scenario performance.",
  "priority": "high",
  "deadline": "2026-08-23",
  "constraints": ["Use only anonymized demo data"],
~~~

## 6. generate_research_report

**Description:** Generate a weekly, meeting, or stage research report from persisted research activities, advisor instructions, and project status. The server returns Markdown and saves the same report under runtime_data/reports/.

Use this when the researcher asks for a weekly update, a group-meeting report, or a stage summary. The tool creates a reliable factual base; the higher-level agent may subsequently improve wording.

### Inputs

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| start_date | string | Yes | Inclusive YYYY-MM-DD start of the activity window. |
| end_date | string | Yes | Inclusive YYYY-MM-DD end of the activity window; must not precede start_date. |
| report_type | string | Yes | weekly, meeting, or stage. |
| project_name | string | No | Overrides the stored project name for this report; otherwise stored status name is used. |

### Successful output

~~~json
{
  "status": "success",
  "report_type": "meeting",
  "report_path": "reports/2026-08-17_to_2026-08-23_meeting_1a2b3c4d.md",
  "generated_at": "2026-08-20T09:45:00+00:00",
  "report": "# Research Report\n\n..."
}
~~~

The report has these eight sections:

1. Phase Goals
2. Completed Work
3. Key Results
4. Current Issues and Risks
5. Learning / Literature Reading
6. Advisor Requirements and Items to Confirm
7. Important Project Decisions
8. Next-step Plan

Activities are selected by the inclusive date range. The current status and currently persisted advisor instructions are incorporated as project context. If no activities match, generation still succeeds and uses explicit “none recorded” style content instead of crashing.

### Example call arguments

~~~json
{
  "start_date": "2026-08-17",
  "end_date": "2026-08-23",
  "report_type": "meeting",
  "project_name": "Adaptive ResearchTwin Demonstrator"
}
~~~

## Error examples

Invalid input is a controlled tool result, not a server crash:

~~~json
{
  "status": "error",
  "error_code": "invalid_date_range",
  "message": "start_date must be on or before end_date."
}
~~~

Other representative error codes include invalid_date, invalid_enum, invalid_limit, invalid_input, duplicate_activity, and storage failures. Agents should correct the input when possible, surface a concise explanation to the researcher when necessary, and never fabricate a successful persistence result.
